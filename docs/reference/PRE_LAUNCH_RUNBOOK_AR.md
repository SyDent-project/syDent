## البند ١ — اختبار استعادة نسخة احتياطية (افعله أولاً)

**لماذا أولاً:** قبل أن تلمس أي مفتاح إنتاج (البندان ٢–٣)، تأكّد أن النسخ الاحتياطية ترجع فعلاً. لو فيها خلل، تريد أن تكتشفه الآن — لا وقت الكارثة. هذا الاختبار لم يُجرَ أبداً حتى تاريخه.

**المتطلبات المسبقة:** وصول لريبو `AyhamGhnaim/SyDent-backups` + القدرة على إنشاء مشروع Supabase مؤقّت (throwaway).

**الخطوات:**
1. من ريبو `SyDent-backups`، اسحب أحدث مجلد نسخة مؤرّخ (يحتوي على dump قاعدة البيانات: الأدوار + المخطّط + البيانات، بما فيها مخطّط `auth`).
2. أنشئ **مشروع Supabase مؤقّتاً جديداً** (مجاني، يُحذف بعد الاختبار). **لا تستعِد فوق الإنتاج.**
3. استعد الـdump إلى المشروع المؤقّت (راجع `SyDent_DR_Runbook.md` ضمن ملفات سياق المالك للأمر الدقيق).
4. تحقّق من سلامة الاستعادة:
   - عدد الجداول مطابق للإنتاج
   - سياسات RLS موجودة (استعلم `pg_policies`)
   - عيّنة بيانات معقولة في الجداول الأساسية (`patients`, `appointments`, `payment_splits`, `clinic_settings`)
   - مخطّط `auth` فيه المستخدمون (حسابات الدخول محفوظة)
5. (اختياري لكن موصى به) اختبر استعادة **ملفات المرضى** من حاوية Cloudflare R2 `sydent-backups` عبر rclone إلى مجلد محلّي، وتأكّد أن ملفاً واحداً على الأقل يُفتح صحيحاً.

**كيف تتحقق أنه نجح:** المشروع المؤقّت يعكس بنية وبيانات الإنتاج، وتقدر تسجّل دخول بحساب تجريبي عليه. عندها احذف المشروع المؤقّت.

**ملاحظة:** اسحب أيضاً مخطّط القاعدة الحيّ كأساس مرجعي حقيقي — ملفات `migrations/` سجلّ تاريخي جزئي فقط (راجع القسم ٥ من وثيقة التسليم).

## البند ٢ — تدوير مفاتيح S3 / R2 (البوّابة الحرجة)

**لماذا إلزامي:** مفاتيح تخزين Supabase (بروتوكول S3) ومفاتيح Cloudflare R2 ظهرت بلقطات شاشة خلال جلسات التطوير. أسوأ سيناريو محدود (وصول لنسخ تجريبية في حاوية `sydent-backups` فقط، لا بيانات إنتاج) — لكن مع دخول بيانات مريض حقيقية يصبح التدوير غير قابل للتأجيل.

**المتطلبات المسبقة:** أنجزت البند ١ (تتأكد أن النسخ تعمل قبل أن تكسر شيئاً) + وصول لـ Supabase Storage + Cloudflare R2 + GitHub repo secrets.

**الخطوات:**
1. **ولّد مفاتيح S3 جديدة في Supabase** (Storage → S3 access keys): مفتاح وصول + سرّ جديدان.
2. **ولّد رمز API token جديد في Cloudflare R2** (مقصور على الحاوية `sydent-backups`، صلاحية القراءة/الكتابة فقط).
3. **حدّث أسرار GitHub** (الريبو → Settings → Secrets and variables → Actions):
   - `SUPABASE_S3_ACCESS_KEY_ID` + `SUPABASE_S3_SECRET_ACCESS_KEY`
   - `R2_ACCESS_KEY_ID` + `R2_SECRET_ACCESS_KEY`
   - (`R2_ACCOUNT_ID` يبقى كما هو — ليس سرّاً يُدوَّر)
   - إن غيّرت كلمة سرّ قاعدة البيانات أيضاً، حدّث `SUPABASE_DB_URL`.
4. **شغّل workflow الـbackup يدوياً** (Actions → backup → Run workflow).
5. **أبطِل المفاتيح القديمة** في Supabase و Cloudflare **بعد** نجاح التشغيل بالمفاتيح الجديدة.

**كيف تتحقق أنه نجح:** تشغيل الـbackup يطلع **أخضر** بالمفاتيح الجديدة، ويظهر مجلد نسخة جديد مؤرّخ في `SyDent-backups` + ملفات مُحدَّثة في حاوية R2. هذا هو الاختبار الحيّ (Rule #19: الاختبار الحيّ هو الحَكَم النهائي).

## البند ٣ — أضِف تاريخ انتهاء لتوكن `BACKUP_PAT`

**لماذا إلزامي:** توكن النسخ الاحتياطي (المسمّى `sydent-backup`) **نطاقه سليم أصلاً** — fine-grained مقصور على ريبو `SyDent-backups` فقط، Contents (Read/Write). المشكلة الوحيدة المتبقّية: **بلا تاريخ انتهاء** (Expiration = Never) = صلاحية مفتوحة دائمة. هذا البند تصحيح صغير لهذه النقطة فقط.

**تحقّق مسبق:** GitHub → Settings → Developer settings → Fine-grained tokens → افتح التوكن `sydent-backup`. لو عمود **Expiration = Never** → نفّذ الخطوات أدناه. (لو سبق وأضفت له انتهاءً، البند منجَز — تخطّاه.)

**الخطوات:**
1. ولّد **GitHub fine-grained PAT جديد** بنفس النطاق تماماً: ريبو `SyDent-backups` فقط · Contents (Read/Write) + Metadata (Read) · **هذه المرة بتاريخ انتهاء** (مثلاً سنة).
2. حدّث سرّ `BACKUP_PAT` بالقيمة الجديدة (الريبو → Settings → Secrets and variables → Actions).
3. شغّل workflow الـbackup يدوياً → تأكّد أنه أخضر.
4. **احذف التوكن القديم بلا انتهاء** من GitHub (Settings → Developer settings → Tokens).

**كيف تتحقق أنه نجح:** الـbackup يطلع أخضر بالتوكن الجديد، والتوكن القديم بلا انتهاء لم يعد موجوداً.

## البند ٤ — تدرّج DMARC: `p=none` → `p=quarantine` → `p=reject`

**لماذا إلزامي:** SPF و DKIM و DMARC جميعها PASS أصلاً، لكن DMARC على `p=none` (مراقبة فقط) لا يحمي فعلياً. التشديد يمنع انتحال نطاقك ووقوع بريدك في صندوق السبام. ابدأ هذا البند **بالتوازي** مع البنود الأخرى لأنه يتطلّب فترة مراقبة.

**المتطلبات المسبقة:** البريد شغّال عبر Resend (custom SMTP على `mail.sydent.app`). سجل DMARC في Cloudflare DNS على `_dmarc.mail.sydent.app`.

**الخطوات (مرحلية):**
1. **راقب أسبوعاً على `p=none`:** افحص تقارير DMARC الـaggregate وتأكّد أن **كل البريد الشرعي يمرّ** (يُحاذي SPF/DKIM). لو لا يوجد مستقبِل للتقارير، أضف `rua=mailto:...` لسجل الـTXT.
2. **شدّد إلى `p=quarantine`:** عدّل سجل TXT في Cloudflare DNS. راقب أسبوعاً آخر — لا بريد شرعي يُحجَب.
3. **شدّد إلى `p=reject`:** بعد التأكد أن كل شيء سليم على `quarantine`.

**كيف تتحقق أنه نجح:** تقارير DMARC تُظهر تحاذياً ١٠٠٪ للبريد الشرعي عبر المراحل، وبريد SyDent يصل صندوق الوارد (لا السبام)، ومحاولات الانتحال تُرفض على `p=reject`.

**ملاحظة:** قرار سعة البريد منفصل — حدّ معدّل Supabase Auth مضبوط على ٤/ساعة ليطابق خطة Resend المجانية. كافٍ لعدد قليل من العيادات، لكن رقِّ Resend (Pro) وارفع الحدّ قبل التوسّع لعملاء كثر (راجع القسم ١٠ من وثيقة التسليم).

## تعريف الإنجاز (Definition of Done)

اعتبر تصليب ما قبل الإطلاق **منجزاً** عندما:

- ✅ اختبار استعادة نُفّذ بنجاح على مشروع Supabase مؤقّت (البند ١)
- ✅ كل مفاتيح S3/R2 مُدوَّرة، والقديمة مُبطَلة، وتشغيل backup أخضر بالجديدة (البند ٢)
- ✅ توكن `BACKUP_PAT` صار له تاريخ انتهاء، والقديم بلا انتهاء محذوف، وتشغيل backup أخضر (البند ٣)
- ✅ DMARC وصل `p=reject` بعد مراقبة سليمة عبر المراحل (البند ٤)

عند اكتمالها، يكون النظام جاهزاً لاستقبال أول عميل حقيقي. (العمل غير الحاجب — المحاور ٤–٦: نظافة الكود، الأتمتة، التوثيق — موصوف في القسم ١٠ من وثيقة التسليم؛ مفيد لكنه لا يمنع الإطلاق.)

## ملاحظة على البريد المخصّص (تحقّق حيّ)

توثيق المالك يشير إلى أن **custom SMTP عبر Resend مُختبَر حياً ✅**، لكن إحدى قوائم المهام تذكره كبند متابعة. **تحقّق حياً لا من التوثيق** (Rule #19): أرسل بريد اختبار من النظام (مثلاً إعادة تعيين كلمة مرور) وتأكّد أنه يصل عبر `mail.sydent.app` بنجاح قبل أن تعتمد عليه للعملاء.
