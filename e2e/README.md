# SyDent — Playwright Smoke E2E (المسار ب)

**المبدأ الحاكم:** الاختبارات **لا تضرب `sydent.app` أبداً.** `dist/` يُبنى محلياً
(`bash scripts/build-dist.sh`) ويُخدَم على `127.0.0.1:8080` ضد Supabase الحقيقي
بمستأجر تجريبي معزول («عيادة E2E الآلية»).

هذا المجلد **معزول كلياً**: الجذر يبقى صفر تبعيات npm، و`build-dist.sh` يستثنيه
من النشر (سطر الاستثناء `db|docs|e2e|migrations|scripts|supabase`).

---

## قرار Turnstile (موثَّق — لا تغيّره بلا فهم السياق)

حماية الكابتشا بـ Supabase **عامة** — تطال `/token?grant_type=password` — فالدخول
بكلمة السر برمجياً محجوب، ومفتاح Turnstile «الاختباري» لا ينفع (التحقق سيرفري
عند Supabase مقابل الـ Secret الحقيقي، وتبديله = تعطيل حماية الإنتاج).

**الحل المعتمد:** `global-setup.ts` يسكّ جلسة عبر مسارين معفيين من الكابتشا:
`POST /auth/v1/admin/generate_link` (magiclink بمفتاح السرّ) ثم استهلاكه
(`POST /verify` بـ token_hash، واحتياطاً `GET action_link` بقراءة الـ fragment).
الجلسة تُكتب بصيغة `sydent.auth` (عقد `supabase-init.js`) داخل
`.auth/state.json` (storageState — untracked). التجديد عبر `refresh_token`
غير محكوم بالكابتشا فتعيش الجلسة طوال التشغيلة.
**صفر تعديل على كود الإنتاج، وصفر كلمة سر بالأسرار.**

## الأسرار (env فقط — لا قيمة في أي ملف بهذا الريبو)

| المتغيّر | ماذا يحمل |
|---|---|
| `E2E_EMAIL` | إيميل مستأجر الاختبار «عيادة E2E الآلية» |
| `E2E_SUPABASE_SECRET_KEY` | المفتاح السري للمشروع (Settings → API) — يذهب لـ GitHub Secrets مباشرة ولا يمرّ بأي محادثة/ملف |
| `E2E_BASE_URL` (اختياري) | افتراضي `http://127.0.0.1:8080` |
| `E2E_SUPABASE_URL` (اختياري) | افتراضي مشروع الإنتاج |

## مستأجر الاختبار (إعداد لمرة واحدة)

1. سجّل «عيادة E2E الآلية» من المتصفح عادياً (Turnstile يدوي مرة واحدة).
2. وافق عليها من لوحة الأدمن + أعلى خطة entitlements + وسمها كي لا تدخل MRR.
3. **بلا PIN إطلاقاً** — كي لا يعترض SyDentLock مسار الاختبارات.

## التشغيل محلياً

```bash
bash scripts/build-dist.sh          # من جذر الريبو
cd e2e && npm ci
npx playwright install --with-deps chromium
E2E_EMAIL=... E2E_SUPABASE_SECRET_KEY=... npx playwright test
```

بالـ CI: workflow يدوي `e2e-smoke` (Actions → e2e-smoke → Run workflow).
الدمج ببوابة النشر (`ci-guards`) = جلسة ب٣ (متدرّج: أسبوعان informational
ثم بوابة حقيقية).
**حالة ب٣ (26 تموز 2026):** المرحلة ١ منفَّذة — الخطوات استُخرجت إلى
`.github/actions/e2e-run` (مصدر الحقيقة الوحيد)، وjob `e2e` بـ`ci-guards`
يعمل informational على كل push إلى main (concurrency `e2e-tenant` مشترك مع
اليدوي، `promote` ما زال `needs: guards` فقط). قلب البوابة الحقيقية بعد
أسبوعي استقرار = سطر واحد: `promote.needs: [guards, e2e]`.

## قواعد ملزِمة للسيناريوهات القادمة (ب٢)

- تنظيف ذاتي: كل اختبار يحذف ما أنشأه (`afterEach` حتى عند الفشل).
- محدّدات `data-test` فقط للعناصر الجديدة — لا نصوص عربية.
- صفر `waitForTimeout` كآلية انتظار أساسية — انتظار حالة (`expect(...).toBeVisible()`).
- `workers: 1` — نفس المستأجر؛ التوازي = تعارض بيانات.

## السيناريوهات (ب٢-أ منجزة)

| # | الملف | يغطّي |
|---|---|---|
| دخان | `tests/smoke.spec.ts` | سكّ الجلسة + الإقلاع (ب١) |
| ١ | `tests/nav.spec.ts` | تنقّل السايدبار ×5 صفحات · gating (`accounting` gateable) · صفر خطأ كونسول |
| ٢ | `tests/patient.spec.ts` | إضافة → **`local_id` بصيغة `P###`** (RPC ذرّي) → فتح الملف → حذف |
| ٣ | `tests/appointment.spec.ts` | حجز عبر اقتراحات المريض → القائمة → تغيير الحالة → حذف |

**التنظيف الذاتي — قرار معماري:** لا نعتمد على واجهة الحذف؛ لو فشل اختبار
بالنصّ تتراكم بيانات وسخة للأبد (والترقيم ذرّي لا يُعاد استخدامه). كل اختبار
يكنس عبر PostgREST بـ**جلسة المستأجر نفسها** (`.auth/ctx.json`) — **لا
service_role**: RLS هي الحارس (Rule #123 محفوظة). كل كيان يُنشأ ببادئة
`E2E-`، و`sweep()` يعمل **قبل وبعد** كل اختبار (`finally`) فيكنس بقايا
التشغيلات الفاشلة السابقة أيضاً. ترتيب الحذف **appointments ثم patients**
(قيد FK) مفروض بـ`cleanupOrder()` ومُبرهَن بـnode.

**إسكات الطرف الثالث — `fulfill 204` لا `abort`:** الإجهاض يولّد بنفسه
`Failed to load resource` بالكونسول فيُفشل توكيد «صفر خطأ» بسبب حجبنا نحن.
الـ204 = طلب نجح فارغاً ⇒ صفر ضجيج وصفر وصول لمشروع Sentry الإنتاجي.

**allowlist ضجيج الكونسول** (`nav.spec.ts`): كل بند بمبرّر مكتوب. أي توسعة
مستقبلية تلتزم بنفس الشرط — **لا يُطفأ التوكيد**.

**سمات `data-test` بكود الإنتاج:** ٨ أسطر بملفين (`patients.html` ×5 ·
`appointments.html` ×3) — **سمات HTML بحتة، صفر CSS/JS يقرأها، صفر تغيير
سلوك** (مُبرهَن: كل سطر بالـdiff يحوي `data-test=`، والـdiff متناظر 8+/8−).

## تقطّع مرصود بـ `generate_link` (ب١) — وسياسة الإعادة

بأول ثلاث تشغيلات: #1 و#2 نجحتا، و**#3 فشلت** بنفس الكومِت ونفس السرّ:

```
E2E generate_link: HTTP 403 {"error_code":"bad_jwt",
  "msg":"invalid JWT ... unrecognized JWT kid <nil> for algorithm ES256"}
```

رفضٌ من طرف Supabase (لا انهيار بكودنا)، وغير حتمي. لذلك تمرّ نداءات
المصادقة الثلاثة عبر `fetchWithRetry` بسياسة `shouldRetryAuth`:
**403 / 5xx / فشل شبكة تُعاد** (٣ محاولات، 1s ثم 3s)، بينما
**401 / 404 / 422 لا تُعاد** كي لا يختبئ خطأ إعداد وراء تأخير.

⚠️ **بصراحة: هذا إصلاح مرجَّح + مسبار تشخيصي لا حلٌّ مؤكَّد.** إن كان
التقطّع يدوم دقائق لا لحظات فلن تنقذه الإعادة. لذلك كل محاولة تُسجَّل
بصوت عالٍ (`attempt N → HTTP X, retrying…` و`✓ (rescued by retry)`) —
فحتى الفشل يورّث معلومة حاسمة. المسارات البديلة عندها: مفتاح سرّي مخصص
للاختبار، أو مراجعة إعدادات JWT للمشروع.

## حدود موثَّقة (مقبولة بقرار)

- **CSP لا تُختبر محلياً:** `_headers` ملف Cloudflare والخادم المحلي لا يطبّقه.
  الرأس مُتحقَّق حياً على الإنتاج (جلسة CSP). خادم يقرأ `_headers` = تعقيد مؤجَّل.
- **Sentry + Turnstile محجوبان بالـ route** داخل الاختبارات — كي لا نلوّث مشروع
  Sentry الإنتاجي بأخطاء localhost ونحرق الحصة.
- **`serviceWorkers: 'block'`:** بدونها `sw.js` يتسجّل على localhost ويكاش
  فترى الاختبارات dist قديماً عبر التشغيلات.
- توكيد «صفر خطأ كونسول» مؤجَّل لسيناريو ١ بـ ب٢ (يحتاج allowlist ضجيج مدروسة).
